# Input History: Connection Audit and Fix Plan

**Project:** Android keyboard, fork of Fossify Keyboard (`SimpleKeyboardIME`, `MyKeyboardView`), modified by the owner.
**Target system:** `InputHistoryRecordingEngine` and `InputHistoryDatabase` (Room: `input_history`, `deletion_events`).
**Audience:** Google AI Studio, working with the full repository.

---

## 0. Ground rules

1. **Phase 1 and 2 are diagnosis and connection repair only.** Do not add features, redesign the engine, or refactor. Feature work starts only after the owner approves the Phase 2 report.
2. **Change as little as possible.** Every fix must be a small, reviewable diff. Explain each one.
3. **Never log typed text.** Debug logs may contain event type, lengths, indices, session id, sequence number, and timestamps. They must not contain characters or words the user typed.
4. **Debug logging must be debug-build only** (`BuildConfig.DEBUG` guard) and easy to remove. Use one tag: `IHDBG`.
5. If something cannot be confirmed from the code, say **"unverified"**. Do not guess and present it as fact.
6. Keep password-field, excluded-app, and master-toggle protections intact at all times.

---

## 1. The problem being investigated

The history recorder shows **deletions correctly, but typed text is missing or incomplete**. Sessions and deletion events appear well ordered. Suspected causes, none yet confirmed:

| # | Hypothesis | Layer |
|---|------------|-------|
| H1 | Only some input paths call the engine (suggestion taps, autocorrect, swipe, paste, emoji, voice, clipboard chip bypass `onKeystroke`). | Capture |
| H2 | `final_text` is built or read after the field is cleared on send, so it is empty or truncated. | Finalization |
| H3 | A send is treated as a mass deletion, so the message is stored as a deletion chunk. | Classification |
| H4 | The engine counter (`charCounter`) drifts from the real field contents, so sessions close at wrong moments. | Session logic |
| H5 | Hooks exist but are not wired (callback never invoked, wrong lifecycle method, engine instance recreated, engine stopped too early). | Connection |
| H6 | Background write receives a shared mutable buffer instead of a copy, or runs after the buffer is reset. | Threading |
| H7 | Session closes and reopens on replace-a-word because the counter touches 0 briefly. | Session logic |

**Goal of Phases 1 and 2:** find out which hypotheses are true, and repair only the broken *connections* (H5, H6, and any plain wiring bug found).

### 1.2 Verify the lifecycle wiring

Check and report on each:

- Where `InputHistoryRecordingEngine` is instantiated. Is there exactly one instance? Is it ever recreated (config change, `onCreate` vs `onStartInput`)?
- `onStartInput`, `onStartInputView`, `onFinishInput`, `onFinishInputView`, `onUpdateSelection`, `onWindowHidden`: which ones call the engine, and is the order correct?
- Is `stopRecording()` called anywhere it should not be (for example on view hide or on every input restart)? Does it wipe buffers mid-session?
- Is the master toggle read at the right time, and does toggling it mid-session behave sanely?
- Are the password check and blocked-package check run in `onStartInput` and also when the field type changes within the same session?
- Does the engine receive the correct `EditorInfo` (package name, input type, field id) every time?

### 1.3 Verify the engine's internal data flow

Read `InputHistoryRecordingEngine.kt` and report:

- How `workingBuffer`, `liveCharIndices`, `pendingDeletions`, and `charCounter` change on each event. Write the exact transitions.
- How `final_text` is computed, **and at what moment** relative to a field clear. Is it taken before or after the buffer is reset?
- Exactly what condition produces `SENT` versus `DISCARDED`, and whether a send can trigger the deletion path first.
- Whether `closeSession` copies data before handing it to the coroutine, or passes live references (H6).
- Whether any state is shared between the main thread and `Dispatchers.IO` without a copy.
- Whether `liveCharIndices` is a stack that assumes edits only at the end (it will break on mid-text edits; note it as a known limitation, do not fix it yet).

### 1.4 Verify the database layer

- Confirm both entities, the DAO methods, the foreign key cascade, and that the database builder opens `input_history.db` correctly.
- Confirm inserts for `input_history` and `deletion_events` happen in one transaction, and that `session_id` is set correctly on events.
- Check for swallowed exceptions (`try/catch` with empty handlers) in the write path.
- Check migrations and schema version. Is there any chance of silent `fallbackToDestructiveMigration`?
- Confirm `InputHistoryActivity` reads `final_text` from the correct column and does not rebuild text from deletion events only.

### 1.5 Phase 1 deliverable

A written report with:
1. The completed table from 1.1 (with file and line references).
2. A list of confirmed wiring bugs.
3. A list of suspected-but-unverified issues.
4. Which hypotheses (H1 to H7) the static read supports, contradicts, or cannot decide.

## Phase 2: Runtime instrumentation and connection repair

### 2.1 Add temporary debug instrumentation (debug builds only)

Add a tiny helper, for example `IhDebug.log(event, fields)`, that writes to Logcat under tag `IHDBG`. Call it at:

| Point | Fields to log (no typed text) |
|---|---|
| Every engine entry method (`onStartInput`, `onKeystroke`, `onBackspace`, `onWordDeleted`, `onFinishInput`, `closeSession`) | event name, session id, seq number, `charCounter`, `workingBuffer.length`, `liveCharIndices.size`, `pendingDeletions.size`, package name, timestamp |
| Every direct `InputConnection` edit in the IME that does **not** call the engine | event name, length of text being committed, `"BYPASS"` marker |
| `onUpdateSelection` | old and new selection start/end, composing region start/end |
| Session close | final status, `final_text.length`, number of deletion events, reason |
| Before DB insert | session id, `final_text.length`, events count, thread name |
| After DB insert | row id, success or exception |

Add a monotonically increasing **sequence number** and a **session id** (in memory) to every log line, so ordering is provable.

### 2.2 Optional: field-length ground truth (debug only)

In debug builds only, after each edit, read the real field length with `getExtractedText` or `getTextBeforeCursor` and `getTextAfterCursor` (length only) and log it next to `charCounter`. This shows **when and by how much the engine counter drifts** from reality. If the editor returns null, log `"EXTRACT_NULL"`.

### 2.3 Run the test matrix

Run each scenario on a real device, one at a time, collect the `IHDBG` log, and then open the saved history row. For each, record: log excerpt (no text), expected row, actual row, pass/fail.

### 2.4 Two-apps test (T13) in detail

1. In app A, type "AAA 111" but do not send.
2. Switch to app B (different app), type "BBB 222", send it.
3. Switch back to A, add " 333", send it.
4. Inspect the database.

**Expected:** two separate sessions, with no leakage between them, and the timestamps may overlap. **Check specifically for:** characters from B appearing in A's `final_text` (or the reverse), A's session being lost at the switch, and the background write seeing a buffer already reset for B (H6). Logs must show A's session sealed **before** B's first keystroke.

### 2.6 Connection repairs (allowed in this phase)

Only repair things that are **wiring or plumbing**, such as:

- A missing call from the IME into the engine on a path that already exists.
- An engine method that is called but with wrong arguments.
- A lifecycle method that stops or resets the engine too early.
- A shared buffer passed to the background coroutine (pass an immutable copy instead).
- `final_text` computed after the buffer reset (compute and copy it first).
- A swallowed exception hiding a failed insert.
- A schema or DAO mismatch causing silently dropped rows.

**Not allowed yet:** new session state machines, cursor-aware buffer rewrite, composing-text handling, delayed-empty logic, encryption, new statuses, UI changes. Those are Phase 3 and need approval.

For every repair: show the diff, say which hypothesis it addresses, and **re-run the relevant tests** to show before and after.

## Phase 3 (not started): feature fixes, for reference only

These are listed so Phase 1 and 2 findings can be mapped to them. **Do not implement.**

1. Treat the real editor text as the source of truth; keep the counter as a helper.
2. Capture initial field text separately from typed text.
3. Cursor-aware edits instead of an end-only stack.
4. Composing-text handling (commit on space, suggestion tap, or focus loss).
5. Delayed empty check, whitespace-only counts as empty, save text before reacting to a clear.
6. Separate live state (active, pending-empty) from final result (SENT, DISCARDED, CLEARED_UNKNOWN, ABANDONED). Mark SENT only with real evidence.
7. Session identity by app plus field, not package alone.
8. Periodic checkpoints and crash recovery.
9. Real character counting (emoji, non-Latin scripts).
10. Privacy hardening: OTP and card fields, incognito flag, encrypted database, backup disabled, auto-delete, history screen lock.
